# 复制历史同步设计

- 日期：2026-11-25
- 分支：`feat/history-sync`
- 前置：`2026-11-10-vault-sync-design.md`（密码本云同步，本设计沿用它的服务器、设备令牌和数据密钥）
- 状态：设计已确认，实现中

## 1. 目标

开启了云同步的设备之间，同步复制历史里的文本条目：新复制的内容、复制时间、收藏、备注和删除。服务器只存密文。

不做：图片同步（安卓读写不了剪贴板图片）、把别的设备复制的内容自动写进本机剪贴板、服务器按时间过期。

## 2. 用户确认的决定

| 问题 | 决定 |
|---|---|
| 同步什么 | 只同步文本；单条超过 256 KiB 的文本只留本机 |
| 同步哪些操作 | 新复制、删除（含"清除历史"）、收藏、备注 |
| 加密 | 用密码本的数据密钥派生的子密钥；所以**只在密码本解锁时同步** |
| 开关 | 设置 › 云同步 里的「同步复制历史」，每台设备各自开启，默认关 |

## 3. 行为

- 开启时本机现有的文本历史全部上传，同时拉取其他设备的。
- 密码本解锁后立即同步一次，之后随密码本同步一起进行：服务器有变化时推送（WebSocket），另外每 30 秒轮询一次。锁定期间的复制在下次解锁时补传。
- 别的设备同步来的条目只进列表，不写进本机剪贴板。
- 按保留时间到期只在本机删除，不影响别的设备；比本机保留期更旧的远端条目不拉进来（收藏除外）。
- 关闭云同步（或本机被吊销后关闭）时，复制历史同步一并关闭，本机历史不变。

## 4. 合并规则

同一段文本在所有设备上是同一条（按文本的 SHA-256 识别，即本机库里的 `hash`）。每条的状态：

| 字段 | 含义 | 合并 |
|---|---|---|
| `copied_at` | 最近一次复制的时间（UTC 毫秒） | 取较大的 |
| `favorite`、`note`、`meta_at` | 收藏、备注和它们最后修改的时间 | 整组取 `meta_at` 较大的；相同时按 `(favorite, note)` 取较大的，保证各设备结果一致 |
| `deleted_at` | 最后一次删除的时间，0 为从未删除 | 取较大的 |

- **存活**：`max(copied_at, meta_at) > deleted_at`。
- **删除**：`deleted_at = meta_at = 现在`，`favorite = false`，`note = ""`。所以删除后再复制同一段文本，它会以未收藏的状态重新出现；在别的设备上删除之后才收藏的，也会重新出现。
- 这个合并满足交换律、结合律和幂等，各设备不论以什么顺序收到，最后的结果都一样。时间取各设备自己的时钟，时钟差几秒只影响"同时修改"时谁胜出。
- 本机按存活与否写入或删除 `clipboard_items` 的那一行；行的 `created_at` 是 `copied_at` 换成本机时区的时间。

## 5. 加密

- 子密钥：`seal_key = HMAC-SHA256(数据密钥, "clipboardx/history/seal/v1")`，`id_key = HMAC-SHA256(数据密钥, "clipboardx/history/id/v1")`。
- 服务器上的 id：`hex(HMAC-SHA256(id_key, hash))`。服务器不能拿常见文本的哈希去验证你复制过什么。
- 记录：JSON `{hash, text?, copied_at, meta_at, favorite, note, deleted_at}`，用 XChaCha20-Poly1305 和 `seal_key` 加密，附加认证数据为 `"clipboardx/history/v1:{id}"`。已删除的记录不带文本，服务器上不再留有被删除文本的密文。
- 收到的记录必须满足：能解密；`id` 等于由记录里的 `hash` 算出的 id；带文本时文本的 SHA-256 等于 `hash`。任一不满足：这一页全部不用，提示"同步数据异常"，本机不变。
- 服务器能看到条数、密文大小和修改时间。没有清单，服务器能隐瞒或回滚某一条，但不能读，也不能伪造。（给历史加清单意味着每复制一次都要重传整份清单，不划算。）
- **数据密钥更换**（修改主密码、重新生成助记词）和其他头部变化：服务器在头部版本变化时清空历史；各设备在密码本采用新头部后，把本机历史全部用新密钥重新加密上传。

## 6. 服务器

- 新表 `history(id TEXT PRIMARY KEY, nonce BLOB, ciphertext BLOB, seq INTEGER)`，独立的计数器 `history_seq`。每个 id 只存最新一份，不比较版本：冲突由客户端合并后再传。
- `GET /v1/history?since=n&header=v`：序号大于 `n` 的记录，按序号排列，每页不超过 4 MiB 密文（至少一条），`{records, seq, more}`。
- `POST /v1/history`：`{header_version, records: [{id, nonce, ciphertext}]}` → `{seq}`。
- 两个接口的头部版本与服务器不一致时返回 409。id 必须是 64 位小写十六进制、nonce 24 字节、密文不超过 2 MiB，否则 400。
- 上传成功后沿用 `/events` 推送一条消息（内容是密码本的序号）：客户端收到任何消息都会同步一轮，事件格式不变，旧客户端不受影响。
- 新客户端连到旧服务器：`/v1/history` 返回 404，开关下方显示"同步服务器需要升级才能同步复制历史"。

## 7. 客户端

- **本机记账**：新表

  ```sql
  history_sync(hash TEXT PRIMARY KEY, copied_at INTEGER, meta_at INTEGER,
               deleted_at INTEGER, local_rev INTEGER, pushed_rev INTEGER)
  ```

  存活条目的文本、收藏和备注仍在 `clipboard_items`，已删除的条目只在这张表里留一行（删除标记，不带文本）。`local_rev != pushed_rev` 表示待上传。`clipboard_items` 表结构不变。
- **记账的位置**：`Database` 里改动条目的方法（`insert_text`、`touch_item`、`toggle_favorite`、`update_note`、`delete_item`、`clear_history`）在同一把锁、同一个事务里记一笔；`cleanup_expired` 删掉到期条目的记账行（不留删除标记，所以不会同步）。只在开关打开时记账。
- **开启**：按本机全部文本条目建立记账，未收藏且无备注的 `meta_at = 0`，否则等于 `copied_at`（两台设备都有同一条时，带收藏和备注的那份胜出）。设置里记下开关、拉取进度 `history_sync_seq` 和上传时的头部版本 `history_sync_header`。
- **关闭**：清空记账表和这三项设置。
- **删除标记**：一直保留（每条只是一个哈希和几个整数）。从服务器收到本机从没有过的条目的删除标记，不保存。
- **一轮同步**（在密码本同步之后，同一个后台线程）：
  1. 头部版本与 `history_sync_header` 不同：全部记账行标为待上传，拉取进度归零。
  2. 拉取：逐页校验、合并、写入本机（一页一个事务），合并结果与服务器的不同则标为待上传；记下进度。
  3. 上传：待上传的行逐批（每批不超过 4 MiB 密文）加密上传；成功后只把上传时读到的版本记为已上传，上传期间又改动的行仍待上传。
  4. 本机有变化时刷新界面。
- **状态**：同步状态多一项 `history_error`，显示在开关下方。

## 8. 测试

- **合并**：交换律、结合律、幂等；删除后再复制、删除后才收藏、同时修改备注。
- **加密**：往返；换 id、换文本、改 `hash` 都被拒绝。
- **记账**：每个改动方法都记账；到期清理不留删除标记；开关关闭时不记账；开启时的初始记账。
- **应用远端记录**：新增、更新、删除、保留期之外的不拉进来、合并后待上传。
- **服务器**：上传与分页拉取、头部版本不一致 409、格式校验 400、头部变化时清空。
- **端到端**：两台设备经真实服务器：复制、收藏、备注、删除、清除历史互相同步；修改主密码后重新上传。
- **界面**：开关在无头 UI 测试里能打开和关闭。

## 9. 限制

- 只在密码本解锁时同步；手机上密码本通常是锁着的，要解锁后才会收发。
- 服务器能看到条数、密文大小和修改时间，能隐瞒或回滚某一条。
- 合并以各设备的时钟为准。
- 服务器上的复制历史留到被删除为止，没有自动过期。
