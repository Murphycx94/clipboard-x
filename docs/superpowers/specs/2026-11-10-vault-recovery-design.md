# 密码本恢复助记词：设计

日期：2026-11-10　状态：已实现（未提交），已按安全审查意见修订

## 1. 目标

忘记主密码时，可以凭一份只由用户自己保管的助记词重置主密码，条目全部保留。助记词明文不保存在任何地方，本机和服务器都没有。同步开启后，新设备只凭助记词就能恢复，不需要旧主密码，也不需要秘密密钥。

用户的选择：

- 词表：BIP39 简体中文，24 个字；
- 创建时强制确认：抄写后填回其中 3 个字；
- 允许新设备独立恢复。

## 2. 密钥

| 名称 | 内容 |
|---|---|
| R | 256 位随机数（`RecoveryKey`）。以 BIP39 写成 24 个字，最后一个字带 8 位校验 |
| KEK_R | SHA-256(`"clipboardx/vault/recovery-kek/v1"` ‖ R)。R 本身是满熵随机数，不需要慢速派生 |
| `recovery_wrap` | XChaCha20-Poly1305(KEK_R, DEK ‖ 秘密密钥?, AAD `recovery-wrap/v1`)，72 或 88 字节 |
| `recovery_sealed` | XChaCha20-Poly1305(DEK, R, AAD `recovery-key/v1`)，72 字节 |

- 两个字段都存在 `vault_meta` 中（新增列，`migrate` 负责升级），并随 `VaultHeader` 上传。两者要么都有，要么都没有。
- `recovery_sealed` 的用途：修改主密码、开启秘密密钥时会更换 DEK，此时设备用旧 DEK 解出 R，再为新 DEK 生成 `recovery_wrap`。这样用户不必重新输入助记词，助记词也一直有效。
- 各密文用不同的 AAD 区分用途，与 DEK 包装、key_check、清单、头部认证互不通用。

## 3. 操作

| 操作 | DEK | 头部 |
|---|---|---|
| 创建时设置（`setup_with_recovery`） | 新建 | — |
| 已有密码本首次设置（`set_recovery_phrase`） | 不变 | 版本 +1，认证值用 DEK 计算；其他设备直接采用 |
| 重新生成 | **更换**，全部条目重新加密 | 版本 +1，认证值用旧 DEK 计算；其他设备暂存头部，等用户输入主密码 |
| 修改主密码、开启秘密密钥（`rekey`） | 更换 | 同上，助记词随新 DEK 重新包装 |
| 用助记词重置（`recover`），未开同步 | **更换**，全部条目重新加密 | — |
| 用助记词重置，已开同步 | **不变**，只用新主密码重新包装 | 版本 +1，认证值用 DEK 计算；其他设备暂存，等新主密码 |

- 已开同步时 `recover` 不更换 DEK：刚加入的设备本地没有条目，没法把它们改用新 DEK 加密，服务器上的记录仍在原 DEK 下。旧数据库副本配上旧主密码仍能解开这个 DEK，但还需要秘密密钥，这是第二道防线。未开同步时，本机持有全部条目，所以更换 DEK，旧副本加旧密码就解不开新内容。
- 有暂存头部时，`recover` **只**认它，而且要求它的封印有效（见 §4），本机未同步的修改能用旧 DEK 解开时一并转移过去。如果助记词只能打开本机旧头部，就报"请输入最新的助记词"，而不是丢弃暂存头部。
- 重新生成时更换 DEK，旧助记词即使配上旧的数据库副本或服务器快照，也只能解开旧 DEK，打不开之后的内容。

## 4. 同步

- **头部封印**：每个头部都带有 `seal` = XChaCha20-Poly1305(本头部的 DEK, header_digest, AAD `header-seal/v1`)，摘要包含版本号。从暂存头部或加入时的头部拿到 DEK 后（不论是用密码还是助记词），必须能用这个 DEK 打开封印、并且摘要一致，才会采用。这样有两个效果：
  - 服务器无法把旧头部改个更大的版本号冒充新头部。旧头部可能仍能用当前密码打开（重新生成助记词时密码不变），也一定能用同一份助记词打开（修改密码时助记词不变）。
  - 服务器无法在这些路径上拼接或去掉助记词字段。
- 加入时收到的封印存在 `vault_sync.joined_seal` 里，第一次解锁（用密码或助记词）时校验，通过后清除，失败就拒绝解锁（`Tampered`）。自己的头部在上传时（`header()`，需要已解锁）计算封印。
- `header_digest` 覆盖两个助记词字段（不含 auth 和 seal）。没有助记词时按空字节串计入，`header_of` 把空字段映射为 `None`，表示方式只有一种。
- `check_header`：`recovery_wrap` 的长度必须在 `WRAP_LENS` 之内，`recovery_sealed` 必须是 72 字节，两者必须同时存在或同时缺失。
- `receive_header`：
  - 版本为本机 +1、认证有效，并且密钥材料与本机相同（`same_keys`：格式、KDF 参数、盐、包装后的 DEK、key_check 都一致）时，由 `take_header` 直接采用，只替换助记词字段、版本和认证值；
  - 其他情况照旧暂存；
  - 函数返回值表示是否暂存，`cloud::sync_once` 据此决定是否继续同步；
  - `take_header` 在同一事务里读取本机元数据、比较、只更新两列，避免覆盖同时发生的改动。
- **同版本分叉**：两台设备在同一版本上各自修改了头部（比如都在离线时设置了助记词），版本号相同但摘要不同。`sync_once` 不再当作"相同"处理，改为 `resolve_header_conflict`：
  - 对方只是换了助记词，且认证有效：采用对方的，并提示本机的助记词已失效、需要重新生成；
  - 其他情况：停止同步并提示，不上传任何记录。
- 服务器可能做什么：
  - **去掉或换掉助记词字段**：摘要不再匹配，被拒绝。
  - **重放旧的助记词字段**：版本号只增不减，被拒绝。
  - **伪造能用用户助记词打开的数据**：需要知道 R，做不到。
- 所有设备都丢失时，没有设备能生成配对码。服务器收到 `SIGUSR1` 会打印一个配对码（`issue_pairing_code`）。能发送这个信号的人已经能读服务器文件，所以没有扩大权限：配对码只能换来设备令牌，令牌只能读写密文。

## 5. 界面

- **创建**：输入主密码 → 显示 4×6 的助记词 → 随机抽 3 个位置填写 → 创建。三步完成之前不写入任何数据。
- **设置 › 恢复助记词**：生成或重新生成。对话框依次显示助记词、要求填回 3 个字、输入主密码。重新生成时提示旧助记词会失效。
- **解锁页**："忘记主密码？"（只在有助记词时显示）。输入助记词，空格和中文标点可有可无，再输入两遍新主密码。
- 助记词只存在于对话框的局部 signal 里，对话框关闭即释放。`RecoveryKey` 和 bip39 的 `Mnemonic` 释放时都会清零。

## 6. 风险与限制

- **助记词等于完整访问权**：无需主密码，也无需秘密密钥。这是设计使然，真正的风险在抄写的纸张。
- **256 位无法暴力破解**，与词表语言无关。没有为助记词设置尝试次数限制，因为不需要。
- **服务器能看出**密码本是否设置了助记词。
- **界面控件中的文字**（显示的助记词、输入框里的内容）无法保证从内存中清零，与主密码输入框相同。
- **不更换 DEK 的情况**：首次设置、已开同步时用助记词重置，这两种情况不更换 DEK。如果怀疑 DEK 已经泄露，应修改主密码或重新生成助记词，这两项都会更换 DEK。
- **重新生成只保护之后的内容**：旧助记词仍能打开此前的备份、服务器快照和尚未同步的设备。若怀疑旧助记词泄露，还应修改重要账号本身的密码。
- **能解锁密码本的人也能得到助记词**：因为 R 被封存在 DEK 下，能解锁的人，或持有 Touch ID 那份 DEK 的人，都能解出 R 和秘密密钥。"不明文保存"仍然成立，但助记词并不独立于主密码。
- **恶意服务器可以阻止同步**：它可以推送一个无法验证的"更新"头部，使同步、设置助记词、用助记词重置都停在"请输入最新的…"。它拿不到任何东西，但可以拒绝服务。这在助记词功能之前就存在：服务器本来就能拒绝服务。
